# Performance cache rollout

## Phase 4 — Redis / KV gate (not implemented by default)

Runtime Cache on Vercel is the primary shared cache layer. On **develop**
(`APP_ENV=develop`) catalog APIs send `Cache-Control: private, no-store` and
runtime entries expire in 60s, so algorithm changes are not pinned across
deploys. After each push to `develop`, CI invalidates preview cache tags
(`catalog`, `degrees`, `degrees-paths`, …) — not a project-wide purge, which
would also hit production.

Runtime entries must use the same tags as `expireCacheOnChange` (for example
`degrees-paths` and `catalog`, not `degrees_paths`). Include the rules version
in the cache key when the ranking contract changes.

Introduce
`@vercel/kv` or Upstash Redis only when **all** of the following are true
after Phases 1–3 are deployed:

1. Vercel Observability → Runtime Cache hit rate stays **below 60%** for 48h
2. p95 for `/api/catalog/*` and quiz recommend remains above target with elevated DB CPU
3. Tuning TTL/tags and `expireTag` hooks did not improve hit rate

Document the decision in the PR before adding KV.

## Feature flags

| Variable | Default | Purpose |
|----------|---------|---------|
| `VITE_USE_CATALOG_STATS_API` | `true` (frontend) | Category pages call `/api/catalog/category-stats`. Set `false` to force GraphQL pagination. If the catalog API fails, the frontend still falls back to GraphQL. |
| `LAUREASI_RUNTIME_CACHE_ENABLED` | `true` (admin) | Disable to force in-process fallback |
| `LAUREASI_USE_CATALOG_STATS_SQL` | `true` (admin) | Set `false` to force Payload pagination fallback |
